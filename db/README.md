# Data platform

One Neon Postgres instance that backs multiple portfolio apps, with a **schema
per app** and **least-privilege roles**. Designed to be multi-app; only schemas
for apps that actually exist are built.

## Why this shape

- **One instance, many schemas.** `pizza.*` and `leads.*` live in the same
  database but are isolated namespaces, so apps never collide and a new app is
  just a new schema.
- **A role per job, scoped to its schema.** No app has more access than it
  needs, which contains the blast radius of any bug or leaked credential:
  | Role | Used by | Can do |
  |---|---|---|
  | `pizza_ro` | the public NL→SQL `/ask` endpoint | read the pizza schema only |
  | `pizza_rw` | placing an order, the nightly cron | read/write the pizza schema |
  | `leads_writer` | the public contact form | INSERT a submission; cannot read any back |
  | `leads_reader` | the authenticated admin view | read submissions |
- **Inventory restocks; sales persist.** A nightly job refills
  `pizza.inventory.quantity` to each item's `baseline_stock`. Orders are never
  wiped; the ledger accumulates, so a visitor can place an order and query it
  back later. Abuse is bounded by rate limiting + input saferails, not by
  deleting sales.
- **The sales history stays current.** The same nightly job adds a few
  synthetic orders for yesterday, so "sales last week" never comes back empty.
  See [Time of day and the nightly orders](#time-of-day-and-the-nightly-orders).

## Files

- `schema.sql`: schemas, tables, indexes. Run **first**.
- `seed.sql`: deterministic synthetic data for the pizza schema (menu +
  inventory + ~24 customers, ~90 orders). Generated by `gen_seed.py`. Run **second**.
- `roles.sql`: the application roles + grants. Run **last** (set passwords first).
- `gen_seed.py`: regenerates `seed.sql` (the menu lives here as editable data).
- `backfill.py`: one-off fixes for an already-seeded live database, run by hand
  from a laptop and never deployed. See [Backfilling a live database](#backfilling-a-live-database).

## Setup (Neon SQL editor)

1. Create a free project at neon.tech; open the **SQL Editor**.
2. Paste and run `schema.sql`, then `seed.sql`, then `roles.sql`
   (after replacing the `REPLACE_ME_*` passwords).
3. Each app connects with its own role's connection string (from Neon → your
   project → Roles/Connection details), stored server-side only.

Regenerate the seed after editing the menu:

```sh
python3 gen_seed.py              # writes seed.sql
python3 gen_seed.py /tmp/x.sql   # or write elsewhere, to diff before overwriting
```

The output is reproducible: every date counts back from a pinned
`ANCHOR = date(2026, 7, 5)` (the day the live seed was generated) instead of
today, and `random.seed(7)` fixes the rest, so re-running the generator never
moves the data. Seeded orders span 2026-04-06 to 2026-07-04.

## Time of day and the nightly orders

All times are New York local (`America/New_York`). The database server runs in
UTC/GMT, so `created_at` (a `timestamptz`) prints in UTC unless converted:
`created_at AT TIME ZONE 'America/New_York'`. Timestamps are always built in SQL
as `(<date>::date + <time>::time) AT TIME ZONE 'America/New_York'`, so the New
York date of every generated order equals its `order_date` and no Python time
zone database is needed on Vercel.

- **`created_at` on seeded orders.** Each seeded order gets a time of day drawn
  from `time_of_day()`: open 11:00 to 22:59, with a lunch peak at noon and the
  busiest hours 18:00 to 19:59. The draw uses its own
  `random.Random(f"tonys-pizza-order-{id}")`, so adding it left every other
  value in `seed.sql` unchanged.
- **Nightly synthetic orders.** `frontend/api/restock.py` is the Vercel cron
  (`0 8 * * *` UTC, about 3 to 4 AM in New York). It restocks inventory, then
  calls `add_synthetic_orders` for yesterday in New York and replies
  `{"ok": true, "restocked": n, "synthetic_orders": k}` (status 500 if
  `CRON_SECRET` is unset or the work fails). For that one day it adds 0 to 2
  orders Monday to Thursday and 1 to 2 Friday to Sunday (about the seed's
  pace of one a day), from the regular
  (non-`Online`) customers, each with 1 to 3 distinct menu items at quantity
  1 to 3, about 1 in 8 `Cancelled` and the rest `Delivered`. It never touches
  inventory.
- **Deterministic and idempotent.** Each day's orders come from
  `random.Random(f"tonys-pizza-day-{day}")`, so a day always gets the same
  orders. Under a transaction-scoped advisory lock, a day that already has an
  order from a regular customer gets nothing more, so a rerun or an overlap
  with `backfill.py catch-up` adds 0. Guest orders (city `Online`) do not count.
- **Order ids.** Among one day's synthetic orders, ids follow time of day.
  Overall they are not in time order: a day's synthetic orders are inserted
  when the cron (or a backfill) runs, after that day's guest orders. Use
  `created_at` for ordering.

## Backfilling a live database

`backfill.py` brings a database seeded before these changes up to date. It
connects with the `pizza_rw` URL from `PIZZA_RW_URL` (or `--url`), uses the
project's virtualenv for psycopg, and **changes no rows without `--apply`** (a
catch-up dry run still advances the id sequences, see below).

```sh
export PIZZA_RW_URL='postgresql://pizza_rw:...'   # pizza_rw, never the owner role

# 1) give the 90 seeded orders the created_at gen_seed.py now writes
.venv/bin/python db/backfill.py retime-seed --backup ~/pizza_retime_backup.csv
.venv/bin/python db/backfill.py retime-seed --backup ~/pizza_retime_backup.csv --apply

# 2) add the nightly synthetic orders for every day since the seed
.venv/bin/python db/backfill.py catch-up --start 2026-07-05
.venv/bin/python db/backfill.py catch-up --start 2026-07-05 --apply
```

- `retime-seed` touches only orders with `id <= 90` whose customer is not
  `Online`, using the exact formula `gen_seed.py` uses. With `--apply` it first
  writes `(id, old created_at)` for every row it changes to the `--backup` CSV
  and refuses to run if that file already exists. A second run changes 0 rows.
  To undo, in `psql`:
  ```sql
  BEGIN;
  CREATE TEMP TABLE old (id int, created_at timestamptz);
  \copy old FROM '~/pizza_retime_backup.csv' CSV HEADER
  UPDATE pizza.orders o SET created_at = old.created_at FROM old WHERE o.id = old.id;
  COMMIT;
  ```
- `catch-up --start DAY [--end DAY]` calls `add_synthetic_orders` from
  `frontend/api/restock.py` (loaded by path, so it is the same code the cron
  runs) once per day, one transaction per day, and prints a per-month summary.
  `--end` defaults to yesterday in New York and cannot be later. Without
  `--apply` each day is rolled back; that still advances the order id
  sequences, so a dry run leaves gaps in future ids (harmless).
- Order does not matter: the cron and `catch-up` skip any day that already has
  synthetic orders, so deploy the new cron first or backfill first.
